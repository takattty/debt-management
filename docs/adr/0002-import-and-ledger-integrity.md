# ADR-0002: 原子的な CSV 確定と残高を壊さない取消

Status: Accepted for invariant design。具体的 CSV 列・上限は各実装 Issue で確定する。

## Context

Excel から移行する担当者が誤りを修正でき、二重取込・二重充当・確定後の書換えを防ぐ必要がある。一部入金・一括入金・手数料差額・過入金があるため、単純な請求の paid フラグでは残高を表せない。

## Decision

CSV は preview と confirm を分ける。preview はサーバー側に Tenant、actor、形式版、内容 hash、解析結果、有効期限を保存する案とし、confirm では参照と制約を再確認して全件を同一 transaction で反映する。無効行があれば全件拒否する。内容 hash と一意な取込識別を用いて同じ内容の再確定・並行確定を防ぐ。DB の一意制約を最終防衛とし、クライアントのボタン制御だけに依存しない。

Invoice と Payment はそれぞれの金額を保持し、AllocationLine に現金充当と明示手数料を分けて記録する。過入金は Payment の未充当残高。取消は原記録を残した Reversal で表す。請求への有効な充当が存在するときは直接訂正しない。

金額は JPY 整数。対象の version と残高を transaction 内で検証し、一括消込が部分的に成功する状態を作らない。請求・入金・消込等の業務更新と AuditEvent を原子的に保存する。

## Alternatives

- 正常 CSV 行だけ先に確定：一部成功の再取込で重複や修正対象の混乱が生じ、合意済みの全件拒否に反する。
- preview の JSON をそのままクライアントから confirm へ返す：検証後の差替えや古い参照を防げない。
- 行を削除して取消：誰が何を戻したか追跡できず、元の消込の再送や二重取消を判別しにくい。
- 残高を自由な更新フィールドにする：根拠取引との整合性が失われる。残高は確定記録から導出し、必要な集計値も同一 transaction で整合させる。

## Consequences

preview の保存期間と削除方針、同内容だが意図的な再取込の扱いを明示する必要がある。銀行明細の transaction_id を架空形式で持ち、内容 hash だけで銀行側の重複を完全に防げるとは主張しない。エラーの一覧ダウンロードでは formula injection を防ぐ。履歴を残すため通常の物理削除を避け、データ初期化は開発用手順として分離する。

EX-I03〜06、EX-M02〜05、EX-M08〜10 が受入例。
